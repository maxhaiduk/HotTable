# План лаб

Тут описано, з чого будувати наступні лаби. Поведінка PostgreSQL тут описана як **очікування** з
документації, її ще не перевіряли на цьому стенді. Цифри й точні повідомлення про помилки
з'являються в README лаби лише після того, як її пройдено під навантаженням.

## Як будувати нову лабу

Взірець: `labs/01-index-on-busy-table/`.

- **Тека `labs/NN-назва/`:**
  - `seed.sql` з даними, згенерованими в базі (`generate_series`, не через ORM);
  - `README.md`: ситуація, критерій успіху, кроки з питаннями, розбір під `<details>`;
  - `check.py`: перевірка кінцевого стану на primary і на репліці.
- **Спершу наївний шлях:** користувач бачить, як ламається, і тільки потім робить правильно.
- **Тривалість операції:** наївна операція має тривати 20+ с, щоб її було видно в `make watch`.
  Якщо коротше, збільшуй `ROWS` або ускладнюй операцію.
- **Перевірка перед здачею:** пройди лабу під `make load` від початку до кінця. Цифри в розборах
  мають бути з цього прогону, а критерій успіху має проходити з запасом: на цій машині паралельно
  працюють інші контейнери, і записи стрибають до кількох секунд через I/O.
- **Запуск:** `make seed LAB=labs/NN-…`, `make check LAB=labs/NN-…`.

## Що додати в інфраструктуру

- **`loadgen`: запити під лабу.** Зараз запити зашиті під `orders`. Потрібен набір запитів на лабу
  (наприклад, `labs/NN/load.py` або змінна `QUERIES=…`) і можливість запускати дві версії
  «застосунку» одночасно (лаба 8).
- **`status.sql`: розмір таблиці, мертві рядки, VACUUM.** Розмір таблиці й bloat,
  `n_dead_tup` з `pg_stat_user_tables`, `pg_stat_progress_vacuum` і `pg_stat_progress_cluster`
  (для лаб 3–5). Не відкривати саму таблицю (`pg_relation_size` бере lock), брати оцінки з
  `pg_class`.
- **`status.sql`: швидкість WAL.** Скільки МБ/с пише primary; помітно на backfill і delete.

## Лаба 2. `ALTER TABLE` і черга блокувань

- **Ситуація:** додати колонку до `orders` (`ADD COLUMN … NULL` виконується миттєво).
- **Що ламається:** будь-який `ALTER TABLE` бере `AccessExclusiveLock`. Якщо таблицю тримає
  транзакція, яку відкрили й забули (`make forgotten-tx`), `ALTER` стає в чергу. За ним у чергу
  стають усі нові запити, навіть SELECT, бо черга блокувань FIFO. Сам ALTER миттєвий, але сервіс
  лежить, поки жива забута транзакція.
- **Правильно:** `SET lock_timeout = '2s'` і повтор у циклі. Перед стартом перевірити довгі
  транзакції. Порівняти з `statement_timeout`.
- **Пастки:** у Doctrine-міграції немає вбудованого повтору; `lock_timeout` для всієї ролі
  зачепить і звичайні запити.
- **Критерій:** колонка додана; `read` і `write` ніколи не були в `STUCK` довше, ніж
  `lock_timeout` + 1 с.

## Лаба 3. Зміна типу колонки: `INT → BIGINT`

- **Ситуація:** `orders.id` має тип `integer`, послідовність близько до 2^31 (`setval` у
  `seed.sql`). Скоро INSERT почнуть падати з `integer out of range`.
- **Що ламається:** `ALTER COLUMN id TYPE bigint` перезаписує всю таблицю й індекси під
  `AccessExclusiveLock`, тобто хвилини повного простою.
- **Правильно:**
  1. нова колонка `id_new bigint`;
  2. тригер, що заповнює її для нових і змінених рядків;
  3. backfill батчами;
  4. `CREATE UNIQUE INDEX CONCURRENTLY`;
  5. коротка транзакція: перейменування і `ADD PRIMARY KEY USING INDEX`;
  6. прибрати стару колонку.
- **Друга частина: які зміни перезаписують таблицю.**
  - `ADD COLUMN … NOT NULL DEFAULT 'const'` миттєвий з PG 11.
  - `DEFAULT clock_timestamp()` чи `gen_random_uuid()` (volatile) перезаписує таблицю.
  - Перезапис видно в `make watch` і за розміром таблиці.
- **Пастки:** FK з інших таблиць на `orders.id` теж треба міняти; тип послідовності; мапінг в ORM.
- **Критерій:** `id` має тип `bigint`, INSERT з id > 2^31 проходить, `write max` без простою.

## Лаба 4. Заповнення колонки в мільйонах рядків

- **Ситуація:** нова колонка `currency` в `orders`, її треба заповнити для 20 млн рядків.
- **Що ламається:** один `UPDATE` означає одну величезну транзакцію:
  - writers, що чіпають ті самі рядки, стоять;
  - таблиця росте майже вдвічі, бо кожен UPDATE створює нову версію рядка;
  - сплеск WAL і відставання репліки;
  - VACUUM не може прибрати мертві рядки, поки транзакція жива.
- **Правильно:**
  - батчі по діапазонах PK (~10k), commit на кожен батч;
  - пауза між батчами, стеження за відставанням репліки;
  - скрипт, який можна безпечно перезапустити з будь-якого місця (`WHERE currency IS NULL`).
- **Що спостерігати:** розмір таблиці, `n_dead_tup`, швидкість WAL, відставання репліки, latency.
- **Критерій:** усі рядки заповнені; таблиця виросла не більше ніж на X %; відставання репліки
  не більше Y с.

## Лаба 5. Видалення й архівація

- **Ситуація:** видалити замовлення, старші за 2 роки (~третина таблиці).
- **Що ламається:**
  - один `DELETE` дає довгу транзакцію, WAL і відставання репліки;
  - місце не повертається ОС, бо звичайний VACUUM лише позначає його вільним;
  - `VACUUM FULL` бере `AccessExclusiveLock`.
- **Правильно:**
  - батчевий `DELETE` по PK, далі VACUUM;
  - як альтернатива, партиції за `created_at` і `DETACH PARTITION … CONCURRENTLY` (PG 14+)
    чи `DROP` старої партиції: миттєво і без bloat.
- **Пастки:**
  - FK без індексу на дочірній колонці: кожен видалений рядок робить seq scan дочірньої таблиці;
  - `ON DELETE CASCADE` на мільйони рядків.
- **Окрема лаба на потім:** перевести наявну таблицю на партиції без простою.

## Лаба 6. Обмеження на брудних даних

- **Ситуація:** `UNIQUE (lower(email))` на `customers`, де вже є дублікати, зокрема ті, що
  відрізняються лише регістром.
- **Що ламається:** `CREATE UNIQUE INDEX CONCURRENTLY` падає наприкінці на першому дублікаті й
  лишає `INVALID` індекс. Поки чистиш, приходять нові дублікати.
- **Правильно:**
  1. знайти дублікати й вирішити, як зливати;
  2. закрити притік нових на рівні застосунку;
  3. CIC унікального індексу;
  4. `ADD CONSTRAINT … UNIQUE USING INDEX` (короткий lock).
- **Той самий патерн для `CHECK`, `NOT NULL` і FK:** `ADD CONSTRAINT … NOT VALID`, потім
  `VALIDATE CONSTRAINT`, який бере слабший lock (`ShareUpdateExclusiveLock`). Порівняти з
  `ADD CONSTRAINT` без `NOT VALID`, який сканує таблицю під сильним lock.
- **Критерій:** обмеження валідне, дублікатів 0, записи без простою.

## Лаба 7. Пагінація і `COUNT(*)`

- **Ситуація:** список замовлень з пагінацією і загальною кількістю.
- **Що ламається:**
  - `OFFSET 1000000 LIMIT 20` читає й викидає мільйон рядків, і кожна наступна сторінка
    повільніша;
  - `SELECT count(*)` на 20 млн рядків триває секунди.
- **Правильно:**
  - keyset: `WHERE (created_at, id) < ($1, $2) ORDER BY created_at DESC, id DESC LIMIT 20` з
    індексом під цей порядок;
  - для кількості: оцінка (`pg_class.reltuples`, `EXPLAIN`), окрема таблиця-лічильник або
    index-only scan.
- **Критерій:** сторінка 50 000 така ж швидка, як перша.

## Лаба 8. Перейменування колонки без даунтайму

- **Ситуація:** `orders.amount` перейменувати на `total_amount`. Застосунок деплоїться
  поступово, тож старі й нові версії працюють одночасно.
- **Що ламається:** `RENAME COLUMN` миттєвий, але стара версія застосунку одразу падає з
  `column "amount" does not exist`.
- **Правильно** (expand → migrate → contract):
  1. нова колонка;
  2. подвійний запис (тригер або застосунок);
  3. backfill;
  4. перемкнути читання;
  5. прибрати стару колонку окремим релізом.
- **Що потрібно від інфраструктури:** два `loadgen` з різними наборами запитів («стара» і «нова»
  версія).
- **Критерій:** жодна з версій не отримала помилку за весь процес.

## Ідеї на потім

- **MariaDB/MySQL-трек:** лаба 1 на MariaDB. Online DDL (`ALGORITHM=INPLACE, LOCK=NONE`), metadata
  lock, відставання репліки на весь час `ALTER`, gh-ost і pt-online-schema-change.
- **VACUUM:** autovacuum не встигає за bloat; довга транзакція тримає xmin; transaction ID
  wraparound.
- **Забутий replication slot:** репліка зникла, слот тримає WAL, диск primary заповнюється.
- **Гарячі рядки:** один рядок-лічильник під конкурентними UPDATE, deadlock-и, `FOR UPDATE SKIP
  LOCKED` для черг.
- **Пул з'єднань:** повільний запит з'їдає всі з'єднання; `max_connections` і PgBouncer.
