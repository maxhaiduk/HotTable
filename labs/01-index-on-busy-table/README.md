# Лаба 1. Індекс на великій таблиці під навантаженням

**Ситуація.** У таблиці `orders` 20 млн рядків (2,2 ГБ). У неї постійно пишуть (~200 INSERT/UPDATE
на секунду) і з неї читають. Новий ендпоінт «останні замовлення клієнта» робить такий запит:

```sql
SELECT id, status, amount, created_at FROM orders
WHERE customer_id = $1 ORDER BY created_at DESC LIMIT 20;
```

Без індексу це повний прохід по таблиці, ~1,5 с на кожен виклик. Треба додати індекс і не
зупинити сервіс.

**Критерій успіху** (перевіряється на кроці 6):
- перевірка зелена: на primary і на репліці є валідний індекс, запит іде через нього без
  окремого сортування, невалідних індексів не лишилось;
- у підсумку навантаження за весь прогін: `write err = 0` і `write max < 10s`. Наївний варіант
  дає ~30 с, тобто весь час побудови. Чому не нуль, з'ясуєш на кроці 2.

## Підготовка

**Як читати навантаження.** `write 200/s p99 7ms`: 200 записів за секунду, 99% з них швидші за
7 мс. `STUCK 12.5s`: найстаріший незавершений запит цього типу чекає вже 12,5 с. Для lookup
показано, скільки тривав останній запит лаби.

**Як читати стан бази:**
1. сесії, крім loadgen, і на що вони чекають (`waits_on`, `blocked_by`);
2. loadgen зведено: скільки сесій чекає на блокування, на що найчастіше чекають (`top_wait`),
   хто блокує;
3. блокування на `orders`;
4. прогрес побудови індексу;
5. індекси (`valid`, `ready`);
6. відставання репліки.

SQL лежить у `tools/status.sql`. Ці самі запити працюють і на проді.

Запусти навантаження. Перш ніж щось міняти, подивись хвилину на навантаження і стан бази й
запам'ятай базову лінію: write p99, lookup, відставання репліки.

## Крок 1. Наївно

У консолі:

```sql
\timing on
CREATE INDEX orders_customer_created_idx ON orders (customer_id, created_at);
```

Поки триває побудова (~30 с), дивись на навантаження і стан бази. Запиши відповіді:

1. Що сталося із записами? А з читаннями?
2. Який lock твоя сесія тримає на `orders` (стан бази, «Блокування»)? Який lock чекають writers?
   Чому одне блокує інше, а SELECT ні?
3. Скільки тривала побудова, і скільки секунд записи стояли? Що це означало б на проді?
4. Що сталося з `lookup` після побудови?

<details><summary>Розбір</summary>

`CREATE INDEX` бере на таблицю `ShareLock` і тримає його всю побудову. `ShareLock` конфліктує з
`RowExclusiveLock`, який беруть INSERT/UPDATE/DELETE, але не з `AccessShareLock` від SELECT. Тому
читання працюють, а всі записи стоять, поки індекс не готовий.

У моєму прогоні побудова тривала 28 с, і всі 28 с було `write 0/s` з `STUCK` до 27,5 с. Lookup
прискорився з 1,3 с до 1 мс. На проді це 28 секунд, коли жоден платіж чи замовлення не
записується. Пул з'єднань застосунку забивається запитами, що чекають, а на більшій таблиці це
хвилини чи години.

Таблиця конфліктів блокувань: документація PostgreSQL, *Explicit Locking → Table-Level Locks*.
</details>

Прибери індекс перед наступним кроком:

```sql
DROP INDEX orders_customer_created_idx;
```

Подумай: який lock бере `DROP INDEX`, і чим це загрожує на проді? Чи можна без цього?

<details><summary>Розбір</summary>

Звичайний `DROP INDEX` бере `AccessExclusiveLock` на таблицю. Він конфліктує з усім, навіть із
SELECT. Сам drop миттєвий, але якщо таблицю тримає довга транзакція, `DROP INDEX` стане в чергу,
а за ним стануть усі нові запити до таблиці (це тема лаби 2). Безпечний варіант:
`DROP INDEX CONCURRENTLY`.
</details>

## Крок 2. Не блокуючи записи

Побудуй той самий індекс так, щоб записи не зупинялися. Документація: `CREATE INDEX`, розділ
*Building Indexes Concurrently*.

1. Який lock тепер на `orders`? Чому він не заважає writers?
2. Які фази проходить побудова («Побудова індексу» в стані бази)? Чому вона довша, ніж на кроці 1?
3. Що показують `valid` і `ready` в індексах під час побудови?
4. Записи не стояли, але `write p99` все одно підскакував. Чому? Підказка: `top_wait` у loadgen.
5. Що відбувається з відставанням репліки?

<details><summary>Розбір</summary>

`CREATE INDEX CONCURRENTLY` (далі CIC) бере `ShareUpdateExclusiveLock`. Він конфліктує лише з іншим
DDL і VACUUM, але не з записами. Ціна за це:

- **Два проходи по таблиці замість одного.** Спершу індекс будується за snapshot (`building
  index: …`), потім validation дописує рядки, що змінились під час побудови (`index validation:
  …`).
- **Очікування між фазами.** CIC чекає завершення транзакцій, які могли не бачити новий індекс
  (фази `waiting for …`).
- **Індекс існує вже під час побудови, з `valid = f`.** Після першого проходу `ready = t`: записи
  вже оновлюють індекс, але запити його ще не використовують.

**Чому p99 записів росте без блокувань.** Побудова пише у WAL ~600 МБ індексу, і commit кожного
запису чекає, поки WAL дійде до диска. У моєму прогоні під час CIC writers чекали на `IO:WalSync`
і `LWLock:WALWrite`, а `log_lock_waits` не записав жодного очікування блокування. Найдовша пауза
запису була 1,5 с проти 28 с на кроці 1. На проді так само: CIC не блокує, але вантажить диск і
CPU. Тому його запускають у тихий час і стежать за latency. Регулятора швидкості для цього в
PostgreSQL немає, на відміну від gh-ost у MySQL.

**Репліка.** Вона не будує індекс сама, а програє WAL, який написав primary. У моєму прогоні
відставання сягало 20 МБ і менше секунди. Для порівняння: у MySQL `ALTER TABLE` на репліці
виконується заново, після того як закінчився на primary, тому вона відстає на весь час побудови.
</details>

Прибери індекс:

```sql
DROP INDEX CONCURRENTLY orders_customer_created_idx;
```

## Крок 3. Пастка: міграція в транзакції

Doctrine Migrations за замовчуванням загортає кожну міграцію в транзакцію. Відтвори це:

```sql
BEGIN;
CREATE INDEX CONCURRENTLY orders_customer_created_idx ON orders (customer_id, created_at);
ROLLBACK;
```

Що сталося? Як написати таку міграцію в Doctrine? Що ти втрачаєш, коли міграція не в транзакції?

<details><summary>Розбір</summary>

`ERROR: CREATE INDEX CONCURRENTLY cannot run inside a transaction block`: CIC сам комітить між
фазами. У Doctrine-міграції це вирішується так:

```php
public function isTransactional(): bool
{
    return false;
}
```

Без транзакції міграція не атомарна: якщо в ній три statement'и і впав другий, перший лишиться.
Тому одна така операція на одну міграцію, і `down()` теж робиться через `DROP INDEX CONCURRENTLY`.
</details>

## Крок 4. Пастка: забута транзакція

Відкрий другу консоль і виконай:

```sql
\i labs/01-index-on-busy-table/forgotten_tx.sql
```

Це сесія, яка відкрила транзакцію, прочитала з `orders` і замовкла: як завислий консольний процес
або psql колеги, відкритий з обіду. Enter поки не натискай. (У терміналі те саме робить
`make forgotten-tx`.)

У першій консолі запусти побудову з кроку 2.

1. Чи закінчується побудова? Яка фаза в «Побудова індексу», і на кого вона чекає (pid)?
2. Чи страждають при цьому записи?
3. Як ти знайшов би винуватця на проді, і що з ним робити?

Тепер натисни Enter у другій консолі й подивись на першу.

<details><summary>Розбір</summary>

Побудова доходить до фази `waiting for old snapshots` і стоїть: вона чекає на pid забутої
транзакції, а сесія CIC чекає на `Lock:virtualxid`. Остання фаза CIC чекає, поки завершаться всі
транзакції зі старішим snapshot, бо інакше вони могли б не побачити рядки нового індексу. Записи
не страждають, але міграція висить, доки транзакція жива, а з нею висить і деплой. У моєму прогоні
CIC тривав 66 с замість 30, рівно до моменту, коли забута транзакція завершилась.

Як знайти винуватця на проді:

```sql
SELECT pid, application_name, client_addr, state, now() - xact_start AS in_tx, query
FROM pg_stat_activity
WHERE xact_start < now() - interval '5 minutes'
ORDER BY xact_start;
```

Що робити далі, залежить від того, чия це сесія: `pg_cancel_backend(pid)`,
`pg_terminate_backend(pid)` або дочекатися. Профілактика: `idle_in_transaction_session_timeout`
для ролей застосунку і перевірка довгих транзакцій **до** старту міграції.
</details>

## Крок 5. Пастка: недобудований індекс

Запусти CIC і через ~20 с перерви його Ctrl+C у консолі. Так буває, коли деплой падає по таймауту
або хтось вбиває процес.

1. Що показує `\d orders`? А індекси в стані бази?
2. Чи використовує такий індекс lookup-запит (`EXPLAIN`)? Чи коштує він щось записам?
3. Повтори міграцію як `CREATE INDEX CONCURRENTLY IF NOT EXISTS …` з тим самим ім'ям. Що
   сталося? Що покаже перевірка?
4. Як прибрати такий індекс і побудувати правильно?
5. Експеримент: прибери індекс і повтори крок 4 (забута транзакція), але перед CIC виконай
   `SET lock_timeout = '3s';`. Що стане з індексом?

<details><summary>Розбір</summary>

Перерваний CIC лишає індекс з позначкою `INVALID` (`valid = f`). Якщо його перервали після
першого проходу, то `ready = t`: кожен запис його оновлює, а запити не використовують, тобто ти
платиш за індекс і нічого з нього не маєш. Через WAL він потрапляє і на репліку.

`IF NOT EXISTS` перевіряє лише ім'я. У моєму прогоні він відповів
`NOTICE: relation "orders_customer_created_idx" already exists, skipping` і завершився успішно, а
індекс лишився `INVALID`, і lookup пішов через `Seq Scan`. Для міграції це найгірший варіант:
«зелена» міграція без індексу. Перевірка це ловить.

Як виправити: `DROP INDEX CONCURRENTLY orders_customer_created_idx;`, потім CIC ще раз. Інший
варіант: `REINDEX INDEX CONCURRENTLY orders_customer_created_idx;`.

**`lock_timeout`.** Його часто радять для міграцій, і для звичайного DDL це правильно. Але CIC чекає
на старі транзакції теж через механізм блокувань (`Lock:virtualxid`), тож `lock_timeout` діє і
там. У моєму прогоні CIC пропрацював 34 с, упав з `canceling statement due to lock timeout` і
залишив `INVALID` індекс. Тобто `lock_timeout` перетворює «висить» на «впав і лишив сміття».
Обидва варіанти треба вміти розібрати, і в обох спершу шукають довгі транзакції.
</details>

## Крок 6. Як на проді

Прибери все, що лишилось від експериментів: серед індексів має лишитися тільки `orders_pkey`.
Зупини й знову запусти навантаження, щоб підсумок рахувався з нуля.

Зроби міграцію так, як зробив би на проді, і дочекайся кінця. Потім запусти перевірку
(«✓ Перевірити» або `make check`) і зупини навантаження. У підсумку має бути `write err = 0`,
`write max < 10s`.

<details><summary>Чекліст</summary>

1. **Чи потрібен індекс і який.** `EXPLAIN (ANALYZE)` запиту; порядок колонок під `WHERE`, потім
   `ORDER BY`. Індекс тільки по `customer_id` теж прибере seq scan, але перевірка покаже, що
   сортування лишилось окремим кроком.
2. **Місце на диску.** Тут індекс займає ~600 МБ, плюс тимчасові файли сортування.
3. **Довгі транзакції.** Запит із кроку 4, до старту.
4. **Налаштування сесії міграції.** `SET statement_timeout = 0;`, якщо в ролі є дефолтний.
   `SET maintenance_work_mem = '1GB';`, щоб сортування менше йшло на диск (у межах вільної
   пам'яті сервера).
5. **`CREATE INDEX CONCURRENTLY`** в окремій нетранзакційній міграції, без `IF NOT EXISTS`, або з
   перевіркою `indisvalid`.
6. **Після міграції.** `indisvalid` на primary, `EXPLAIN` запиту, latency записів, репліка.
</details>

## Що відповісти на інтерв'ю

Спершу напиши свою відповідь, 5–7 речень, не підглядаючи. Потім порівняй.

<details><summary>Приклад відповіді</summary>

Спершу перевірю, що індекс справді потрібен: `EXPLAIN (ANALYZE)` запиту і вибір колонок під
`WHERE` та `ORDER BY`. Звичайний `CREATE INDEX` тримає на таблиці `ShareLock` весь час побудови,
тобто записи стоять хвилинами, тому на живій таблиці в PostgreSQL використовую
`CREATE INDEX CONCURRENTLY`. Він не блокує записи, але проходить таблицю двічі, вантажить диск і
WAL і не може працювати в транзакції. У Doctrine це окрема міграція з `isTransactional(): false`.

Перед стартом перевіряю довгі транзакції в `pg_stat_activity`, бо CIC чекатиме на них у кінці.
Під час побудови дивлюся `pg_stat_progress_create_index`, latency записів і відставання реплік.
Якщо побудова впала чи її перервали, лишається `INVALID` індекс, який оновлюється на записах, але
не працює для читання. Його треба видалити через `DROP INDEX CONCURRENTLY` і побудувати знову;
`IF NOT EXISTS` його мовчки пропустить. Після міграції перевіряю `indisvalid` і план запиту.

У MySQL та сама задача: online DDL (`ALGORITHM=INPLACE, LOCK=NONE`) з metadata lock на початку і в
кінці та відставанням реплік на весь час побудови, а для великих таблиць gh-ost або
pt-online-schema-change.
</details>
