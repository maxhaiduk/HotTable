# Веб-інтерфейс для лаб

Лаби як «кімнати» на кшталт TryHackMe. Зліва кроки з питаннями й полями для відповідей, справа
живі графіки навантаження, стан бази й вбудований psql. Терміналу більше не треба, а
`make`-флоу лишається робочим.

## Що беремо з TryHackMe і що додаємо

| TryHackMe                 | Тут                                                                                   |
|---------------------------|---------------------------------------------------------------------------------------|
| Room                      | Лаба                                                                                  |
| Task + поле для відповіді | Крок + питання. Відповідь може звірятися з власним прогоном: «скільки секунд стояли записи?» |
| AttackBox (VM у браузері) | Вбудовані psql-термінали                                                              |
| Прогрес, бейджі           | Прогрес по кроках, зелені галочки від перевірок                                       |
| —                         | Живі графіки, граф «хто кого блокує», таймлайн подій                                  |

## Межі

- Тільки локально, один користувач, без авторизації: `make ui` → http://localhost:7070.
- База й репліка — той самий `docker compose`, що й для `make`-флоу.
- Кожна панель уміє показати SQL, з якого вона побудована: ці самі запити працюють на проді.

## Архітектура

```
Browser (React SPA)
  ├─ текст лаби, питання, прогрес ──── REST ─────┐
  ├─ графіки, стан бази ────────────── WebSocket ┤
  └─ термінали (xterm.js) ──────────── WebSocket ┤
                                                 ▼
          labd: Go, один бінарник із вбудованим фронтом
  ┌──────────┬───────────┬────────────┬────────────┬───────────┬─────────┐
  │ lab      │ load      │ observe    │ term       │ check     │ control │
  │ lab.yaml │ горутини, │ раз на     │ PTY +      │ SQL-тверд-│ up/seed/│
  │ + md     │ pgx       │ секунду    │ compose    │ ження     │ reset   │
  │          │ → метрики │ → стан     │ exec       │           │         │
  └──────────┴───────────┴────────────┴────────────┴───────────┴─────────┘
        │ SQLite (прогрес)            │ pgx              │ docker compose
        ▼                             ▼                  ▼
                        primary ──WAL──▶ replica, console
```

### Модулі `labd`

- **lab.** Читає `labs/NN-*/lab.yaml` і markdown лаби.
- **load.** Генератор навантаження на горутинах із пулом pgx.
  - Навантаження лаби задається у `lab.yaml`: групи (`write`, `read`, `lookup`), кількість
    воркерів, темп, скрипти з вагами.
  - Скрипти пишуться у форматі pgbench: `\set id random(1, :max_order_id)`, далі SQL з `:id`.
    Ті самі файли запускаються справжнім `pgbench` з `-D max_order_id=…`.
  - Змінні на кшталт `max_order_id` рахуються SQL-запитами з `lab.yaml` один раз на старті.
  - Метрики за кожну секунду по кожній групі: кількість, помилки, p50/p99/max, `stuck`
    (найдовше очікування серед незавершених запитів).
- **observe.** Раз на секунду знімає стан бази тими самими запитами, що й `tools/status.sql`:
  сесії, блокування на таблиці лаби, прогрес побудови індексу, індекси, репліка.
- **term.** Термінал = `docker compose exec console psql` під PTY, з'єднаний з xterm.js через
  WebSocket. Окремий сервіс `console` (образ `tools`, працює постійно) має доступ до файлів
  проєкту і до обох серверів.
  - Скільки завгодно сесій на primary, плюс одна на репліці.
  - Кожен psql має мітку `-v labd_term=<id>`. Коли вкладку закривають, `labd` завершує свій
    psql у контейнері: сама зупинка `docker compose exec` цього не робить, і покинута сесія
    тримала б транзакцію вічно. Залишки попередніх запусків `labd` прибирає на старті.
- **check.** Зараз запускає `check.py` лаби в `console`, як `make check`. На етапі 2 це будуть
  декларативні SQL-перевірки з `lab.yaml`.
- **Текст лаби.** Один README для обох способів роботи: `<!-- terminal -->…<!-- /terminal -->`
  потрібне лише в терміналі, і UI це ховає; `<!-- ui … -->` потрібне лише в UI, і звичайний
  markdown цього не показує. Кроки називають ролі («навантаження», «стан бази», «консоль»), а не
  номери терміналів.
- **control** (етап 3). Кнопки запуску, seed з прогрес-баром, reset лаби.
- **events** (етап 3). Зі стану й метрик виводяться події: «почався DDL з таким-то lock»,
  «записи стоять N с», «індекс став INVALID». Вони ставлять позначки на графіках, зараховують
  кроки й дають персональні відповіді на питання.

### Протокол

| Шлях             | Що                                                                  |
|------------------|---------------------------------------------------------------------|
| `GET /api/lab`   | Метадані лаби і її README (markdown)                                |
| `POST /api/load` | `{"running": true/false}`: запустити або зупинити навантаження      |
| `GET /api/load`  | Чи працює навантаження і підсумок поточного прогону                 |
| `POST /api/check`| Запускає перевірку лаби: `{"ok", "output"}`                         |
| `WS /ws/live`    | Раз на секунду: `{"t", "load": {…групи…}, "db": {…стан…}}`          |
| `WS /ws/term`    | Байти терміналу в обидва боки; `{"resize": [cols, rows]}` текстом   |

## Стек

| Шар            | Вибір                                                   | Чому                                                                          |
|----------------|---------------------------------------------------------|-------------------------------------------------------------------------------|
| Бекенд         | Go: pgx, coder/websocket, creack/pty, `embed`           | Конкурентне навантаження з точними latency, один бінарник із фронтом         |
| Фронт          | React + TypeScript + Vite, Tailwind                     | Найбільша екосистема для решти пунктів                                        |
| Термінал       | xterm.js                                                | Стандарт: на ньому зроблений термінал VS Code                                 |
| Графіки        | uPlot                                                   | Тисячі точок у реальному часі без лагів, ~50 КБ                               |
| Граф блокувань | React Flow (етап 3)                                     | Ланцюжок `pg_blocking_pids` як граф                                           |
| Прогрес        | SQLite, `modernc.org/sqlite` без CGO (етап 2)           | Локально, один файл                                                           |

## Розкладка репозиторію

```
cmd/labd/          точка входу
internal/lab/      lab.yaml
internal/load/     генератор навантаження, pgbench-скрипти
internal/observe/  стан бази
internal/term/     PTY ↔ WebSocket
internal/server/   HTTP, WebSocket, роздача фронту
web/               React + Vite; web/dist вбудовується в бінарник
labs/NN-*/         lab.yaml, load/*.sql, README.md, seed.sql
```

## Етапи

1. **MVP** (зроблено). `labd` з load, observe, term. Сторінка лаби: README, живі графіки, стан
   бази, psql-вкладки, кнопки навантаження й перевірки. `make ui` — єдина команда в терміналі:
   він піднімає стенд і заливає дані, якщо таблиці лаби ще немає.
2. **Контент.** `lab.yaml` з кроками й питаннями, підказки, розбори, прогрес у SQLite,
   перевірки з галочками. README для `make`-флоу генерується з `lab.yaml`. `make load` переходить
   на Go-генератор, а `tools/loadgen.py` зникає.
3. **Події.** Таймлайн, автоматичне зарахування кроків, персональні відповіді, граф блокувань,
   кнопки керування стендом.
4. **Каталог лаб**, оформлення, далі лаба 2 одразу у форматі для UI.

## Ризики

- Go-генератор має поводитися як Python-версія, яку перевірено на лабі 1. Звіряємо на кроці 1:
  наївний `CREATE INDEX` має показати зупинку записів на весь час побудови.
- `labd` працює на тій самій машині, що й база, і сам є частиною навантаження.
